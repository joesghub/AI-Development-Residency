# Build Plan: MVP #1 (v2)

> 🔄 **What changed and why (v1 → v2)**
> 
> - **Four new decisions resolved** for the Patiencents loop: how Buy Days are calculated, when leftovers are confirmed, how wishlist items are matched to transactions, and how product details are read from links.
> - **New money rules** so every number stays real and nothing is counted twice, including how Buy Day purchases are paid from the Pot.
> - **Data model updated:** `parked_items` is replaced by `wishlist_items`, `daily_results`, `pot_ledger`, and `transaction_matches`. Buckets are renamed Bills, Essentials, and Usuals.
> - **Scheduled jobs expanded:** daily close, leftover confirmation, Buy Day reminders, and Kept your patience checks.
> - **Security additions:** users can't write their own Pot entries, and link reading is protected against misuse.
> - **Unchanged:** the required technology, three-tier architecture, Plaid and CSV decision, notification approach, Supabase scheduler, GitHub workflow, environments, and MVP costs.

> 🏗️ **Purpose:** Define *how* MVP #1 will be built: a three-tier architecture hosted on Vercel, with data in Supabase, code in GitHub, and secure user accounts.
>

| Database | **Supabase** | Stores data, handles user accounts, runs scheduled jobs |
| Code repository | **GitHub** | Stores code, tracks changes, triggers deployments |

## Three-Tier Architecture

| Tier | What It Does | Technology | What Lives Here |
| --- | --- | --- | --- |
| **1. Presentation** | What the user sees and taps | Next.js (React) web app on **Vercel**, set up as a progressive web app | Today's Number, the Patience Pot, wishlist and Buy Days, welcome-back summary, settings |
| **2. Application** | Business logic and secure connections | Next.js server functions on **Vercel** | Today's Number, daily close, Buy Day scheduling, transaction matching, link reading, Plaid connection, notifications |
| **3. Data** | Stores everything securely | **Supabase** (PostgreSQL, Auth, scheduler) | Accounts, transactions, daily results, Pot ledger, wishlist, matches, bills |

**External services:** **Plaid** for bank connections (application tier only, never the browser) and **Web Push** for notifications.

**How a request flows:** the user opens the app (presentation) → the app sends a request with the user's login token (application) → the server checks the user's identity and queries only that user's data (data) → row-level security enforces the same rule in the database → the server returns results to the screen.

## New Decisions (v2)

### Decision 5: How Today's Number and the Pot work together

**Decision:** Leftovers move into the Pot instead of raising future daily numbers, so no money is counted twice.

**Today's Number** = (income for this pay period − Bills due this period − estimated Essentials − Usuals spent so far this period − amounts already added to the Pot this period) ÷ days left until payday

| Rule | Why |
| --- | --- |
| Unspent money from today goes into the Pot | It's kept, and can't also be spent later as part of Today's Number |
| Overspending lowers the next few days' numbers | The Pot and Total Kept are **never reduced** by overspending (design principle 4) |
| A matched wishlist purchase is paid from the Pot Balance first | Buy Day purchases don't eat into Today's Number |
| If the Pot can't cover the full price (for example, an item bought early), the remainder counts as Usuals spending | Keeps the math honest without making the Pot negative |
| Total Kept only counts confirmed leftovers | It's an achievement that never goes down; buying on Buy Day lowers Pot Balance, not Total Kept |

### Decision 6: When leftovers are confirmed

**Decision:** Show the leftover as pending the next morning, then confirm it three days later.

| Step | What Happens |
| --- | --- |
| **Daily close** (midnight in the user's time zone) | Leftover = Today's Number − Usuals spent that day (never below $0). It's saved as **pending** and shown the next morning: "Yesterday you kept $9." |
| **Confirmation** (three days later) | The leftover is recalculated using the posted transactions for that day. The final amount is written to the Pot ledger as **confirmed**: "Confirmed! Your Buy Day moved 1 day closer." |
| **Late transactions** (arriving after confirmation) | Counted toward upcoming days' spending; the confirmed Pot entry is never reduced |

*Why three days:* bank transactions usually post within one to two days; three leaves a buffer while still feeling timely. This is a starting value to adjust based on MVP data.

### Decision 7: How Buy Days are calculated

**Decision:** A simple projection based on the Pot Balance and recent confirmed leftovers.

1. **Order:** wishlist items are funded in the user's chosen order (newest last by default; users can drag to reorder).
2. **Projected daily leftover:** the average confirmed leftover over the last 14 days. With less than 7 days of history, use an estimate of 15% of Today's Number, labeled "estimated."
3. **Buy Day:** for each item, the day the projected Pot Balance covers the combined price of that item and every item ahead of it.
4. **Ready now:** if the Pot already covers it, the Buy Day is today.
5. **No progress yet:** if the projected leftover is $0, show "Buy Day coming soon. Every dollar you keep gets you closer." No date, no failure message.
6. **Recalculation:** daily, after confirmations. Changes that move a Buy Day **closer** are announced; changes that move it later update quietly, with a gentle weekly summary.

### Decision 8: How wishlist items are matched to transactions

**Decision:** Score each possible match on merchant, amount, and date, with user confirmation for uncertain matches.

| Signal | Points | Rule |
| --- | --- | --- |
| **Merchant** | 2 | The transaction's merchant matches the item's store (from the link's website, or entered by hand). Plaid's cleaned merchant names are used where available. |
| **Amount** | 2 | Within 15% of the item's price, allowing for tax and shipping |
| **Date** | 1 | Between the date the item was added and 7 days after its Buy Day |

| Score | Result |
| --- | --- |
| **4–5 (high)** | Matched automatically, with an undo option |
| **3 (medium)** | "Was this your headphones?" Swipe to confirm or dismiss |
| **0–2** | No match |

| Outcome | Rule |
| --- | --- |
| **Bought on purpose** | Matched on or after the Buy Day |
| **Bought early** | Matched before the Buy Day (tracked for the KPI, never shown as a failure) |
| **Kept your patience** | The Buy Day reminder was sent, there's no response, and no match of score 3+ within 7 days after the Buy Day |
| **Combined orders** | Users can link a transaction to an item by hand |

### Decision 9: How product details are read from links

**Decision:** The server reads basic product details from the link, with manual entry as a fallback.

- When a user shares or pastes a link, a server function opens the page and reads the product name, image, and price from the page's standard sharing information, where the store provides it.
- The **merchant** comes from the link's website address.
- Many stores block automated access, so if details can't be read, the user types the name and price. That takes a few seconds and keeps the feature reliable.

## Money Rules Summary

| Number | Calculated From | Can It Go Down? |
| --- | --- | --- |
| **Today's Number** | Income, Bills, Essentials, Usuals spending, Pot additions | Yes, after overspending, gently and spread across days |
| **Pending leftover** | Today's Number − Usuals spent that day | Recalculated at confirmation |
| **Pot Balance** | Confirmed leftovers − wishlist purchases | Yes, only when a wishlist item is bought |
| **Total Kept** | Sum of confirmed leftovers | **Never** |

## Data Model (v2)

*Every table is tied to a user, with row-level security so users can only access their own rows.*

| Table | What It Stores | Change |
| --- | --- | --- |
| **profiles** | Name, time zone, payday schedule, income, notification time, last active date | Unchanged |
| **bank_connections** | Plaid connection details; access tokens encrypted and readable only by the server | Unchanged |
| **accounts** | Linked bank accounts | Unchanged |
| **transactions** | Amount, merchant, date, bucket (Bills, Essentials, Usuals), source (Plaid or CSV), pending or posted | Buckets renamed |
| **bucket_rules** | Merchant corrections | Unchanged |
| **daily_results** | Date, Today's Number, Usuals spent, leftover, status (pending or confirmed) | 🆕 New |
| **pot_ledger** | Every Pot entry: confirmed leftover, wishlist purchase, or adjustment, with amount and date | 🆕 New |
| **wishlist_items** | Name, price, link, merchant, image, reason, order, Buy Day, status (waiting, bought on purpose, bought early, kept your patience) | 🆕 Replaces `parked_items` |
| **transaction_matches** | Transaction, wishlist item, score, confirmed by user (yes or no) | 🆕 New |
| **bills** | Name, amount, next due date | Unchanged |
| **push_subscriptions** | Device notification registrations | Unchanged |
| **checkins** | Money stress scores | Unchanged |
| **events** | Key actions for KPIs | Unchanged |

**Calculated, not stored:** Total Kept, Pot Balance, and Buy Days are calculated from the tables above, so they always match the underlying records.

## Scheduled Jobs (v2)

*One hourly Supabase job calls a secure Vercel function, which runs whatever is due for each user based on their time zone.*

| Job | When | What It Does |
| --- | --- | --- |
| **Morning notification** | User's chosen time (default 8 a.m.) | Sends Today's Number and the next Buy Day countdown |
| **Daily close** 🆕 | Midnight, user's time zone | Calculates the pending leftover |
| **Leftover confirmation** 🆕 | Three days after each day | Confirms leftovers and writes them to the Pot ledger |
| **Buy Day recalculation** 🆕 | After confirmations | Updates Buy Days; announces any that moved closer |
| **Buy Day reminder** 🆕 | Morning of each Buy Day | "It's Buy Day! Still excited about the headphones?" |
| **Kept your patience check** 🆕 | Seven days after each Buy Day | Confirms unbought items as kept your patience |
| **Transaction sync** | Daily, plus Plaid's update notifications | Imports new and updated transactions, then runs matching |
| **Bill reminders** | Three days before due dates | Sends reminders |
| **Day-30 check-in** | 30 days after signup | Money stress check-in |
| **Monthly recap** | First day of each month | Sends the recap |

## Security Plan (v2)

| Area | Approach | Tier |
| --- | --- | --- |
| **Authentication** | Supabase Auth with email and password or magic link; passwords hashed by Supabase | Data |
| **Data isolation** | Row-level security on every table | Data |
| **Pot integrity** 🆕 | Users can **read** their Pot ledger and daily results but never write to them; only server functions can, so "every number is real" can't be tampered with | Data, Application |
| **Safe link reading** 🆕 | The link reader only opens public web addresses, never internal ones, with time and size limits, so it can't be misused to reach private systems | Application |
| **Server-only secrets** | Supabase admin keys and Plaid secrets only in Vercel environment variables | Application |
| **Bank connections** | Users log in through Plaid's secure window; the app never sees bank passwords | External |
| **Plaid access tokens** | Encrypted, readable only by server functions | Data, Application |
| **Encryption in transit** | HTTPS everywhere | All |
| **Scheduled job security** | Requests must include a secret key | Application |
| **Secrets in code** | Kept out of the repo; GitHub secret scanning enabled | GitHub |
| **Minimal data** | Store only what features and KPIs need | All |
| **User control** | Users can disconnect their bank and delete their account and all data | All |
| **Dependency safety** | GitHub Dependabot alerts | GitHub |
