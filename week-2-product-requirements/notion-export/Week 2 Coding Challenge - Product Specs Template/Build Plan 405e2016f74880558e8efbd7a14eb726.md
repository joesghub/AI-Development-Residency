# Build Plan: MVP #1

> 🏗️ **Purpose:** Define *how* MVP #1 will be built: a three-tier architecture hosted on Vercel, with data in Supabase, code in GitHub, and secure user accounts. This plan resolves the open decisions from the Handoff to Build Plan and sets up the Epics, Features, and Tasks.
> 

## Required Technology

| Requirement | Tool | Role |
| --- | --- | --- |
| Hosting | **Vercel** | Hosts the web app and the server logic |
| Database | **Supabase** | Stores data, handles user accounts, runs scheduled jobs |
| Code repository | **GitHub** | Stores code, tracks changes, triggers deployments |
| User accounts | **Supabase Auth** | Secure sign-up and login |

## Three-Tier Architecture

A three-tier architecture separates the app into three layers, each with one job. This keeps the system secure (users never touch the database directly) and easier to maintain.

| Tier | What It Does | Technology | What Lives Here |
| --- | --- | --- | --- |
| **1. Presentation tier** | What the user sees and taps | Next.js (React) web app on **Vercel**, set up as a progressive web app | Screens for Today's Number, Park It, the welcome-back summary, and settings; the home screen icon and push notification setup |
| **2. Application tier** | The "brain": business logic and secure connections | Next.js server functions on **Vercel** | Today's Number calculation, bucket sorting rules, Plaid connection, notification sending, CSV import processing |
| **3. Data tier** | Stores everything securely | **Supabase** (PostgreSQL database, Auth, scheduled jobs) | User accounts, transactions, parked items, bills, Money Kept, check-ins |

**How a request flows:**

| Step | What Happens |
| --- | --- |
| 1 | The user opens the app and sees Today's Number (presentation tier) |
| 2 | The app asks the server for the user's data, along with their secure login token (presentation → application) |
| 3 | The server checks the user's identity and queries only that user's data (application → data) |
| 4 | The database enforces that rule again with row-level security, returning only rows owned by that user (data tier) |
| 5 | The server calculates Today's Number and sends it back to the screen (application → presentation) |

**External services:**

| Service | Purpose | Connects To |
| --- | --- | --- |
| **Plaid** | Secure bank connections and transaction data | Application tier only, never the browser directly |
| **Web Push** | Morning Number, Park It, and bill reminder notifications | Application tier sends; the user's device receives |

## Resolved Decisions

### Decision 1: How transactions get into the app

**Decision:** Plaid live bank sync as the main path, with CSV import as a fallback.

**Why:**

- Live sync is essential to the low-effort promise (pain point P1); manual import would rebuild the very effort we're trying to remove.
- The Plaid Sandbox is a free, fully featured environment for development and testing, so the entire integration can be built at no cost.
- For real beta users, Plaid offers a Trial plan for U.S. and Canadian developers who sign up on or after April 15, 2026: a free way to use Plaid with real production data. But the Trial plan is limited to 10 Items, meaning roughly 10 connected bank accounts.
- **So the MVP beta works in two tracks:** up to 10 testers use live Plaid sync, and additional testers use CSV import. Comparing the two groups also gives a useful insight: how much automation actually affects retention.
- CSV import also covers users who won't link a bank account, one of the MVP decision gates.

### Decision 2: How transactions are sorted into buckets

**Decision:** Simple rules, not AI, for the MVP.

**Why:**

- Plaid already labels each transaction with a spending category, and those categories map to Bills, Needs, and Wants with a simple lookup table.
- Recurring charges are labeled Bills.
- When a user swipes to correct a transaction, the app remembers that merchant and applies the correction automatically next time.
- Rules are free, predictable, and easy to test. AI categorization is deferred until MVP data shows whether rules are accurate enough.

### Decision 3: How notifications are sent

**Decision:** Web push notifications as the main channel, with in-app messages as the fallback.

**Why:**

- Web push lets the app come to the user (design principle #1) without building a native app.
- On iPhone, web push only works once the user adds the app to their home screen, so onboarding must guide users through that step.
- Users who skip it still see the same information in the app when they open it.

### Decision 4: How scheduled jobs run

**Decision:** Use Supabase's built-in scheduler, not Vercel Cron.

**Why:**

- Several features run on a schedule: the Morning Number, the Park It 48-hour prompt, bill reminders, and daily transaction syncs.
- On Vercel's free plan, cron jobs can only run once per day, and a job set for 1 a.m. can trigger anytime between 1:00 and 1:59 a.m. That can't deliver a Morning Number at each user's local morning across time zones.
- Supabase's scheduler can run every hour at no extra cost. Each hourly run calls a secure server function on Vercel, which sends notifications to users whose local morning or 48-hour deadline has arrived.
- This keeps the three tiers clean: the scheduler triggers the work, and the application tier does it.

## Data Model

*Every table is tied to a user, and row-level security ensures users can only access their own rows.*

| Table | What It Stores | Notes |
| --- | --- | --- |
| **profiles** | Name, time zone, payday schedule, income estimate, last active date | Last active date powers the welcome-back summary |
| **bank_connections** | Plaid connection details | Access tokens are encrypted and readable **only by the server**, never sent to the browser |
| **accounts** | The user's linked bank accounts | Name, type, balance |
| **transactions** | Imported transactions | Amount, merchant, date, bucket, source (Plaid or CSV) |
| **bucket_rules** | The user's merchant corrections | For example, "Spotify → Bills" |
| **parked_items** | Park It entries | Item, price, date parked, decision (bought or skipped), decision date |
| **bills** | Detected recurring bills | Name, amount, next due date |
| **push_subscriptions** | Device notification registrations | One per device |
| **checkins** | Money stress scores | Taken at signup and day 30 |
| **events** | Key actions for KPIs | For example, "app opened," "item parked," "returned after lapse" |

**Calculated, not stored:**

- **Money Kept:** the total of all skipped parked items.
- **Today's Number:** (expected income − upcoming bills − estimated needs − Wants already spent this pay period) ÷ days until next payday. It's recalculated each morning, so overspending one day gently lowers the next day's number rather than breaking the budget.

## Security Plan

*The app stores financial data tied to user accounts, so security is built into every tier.*

| Area | Approach | Tier |
| --- | --- | --- |
| **Authentication** | Supabase Auth with email and password or magic link; passwords are hashed by Supabase and never stored by our code | Data |
| **Data isolation** | Row-level security on every table, so each user can only read and write rows they own | Data |
| **Server-only secrets** | Supabase admin keys and Plaid secrets live only in Vercel environment variables, never in the browser or in GitHub | Application |
| **Bank connections** | Users log in to their bank through Plaid's secure window; our app never sees bank passwords | External |
| **Plaid access tokens** | Encrypted in the database and only readable by server functions | Data, Application |
| **Encryption in transit** | All traffic uses HTTPS (automatic on Vercel and Supabase) | All |
| **Scheduled job security** | Scheduled requests must include a secret key, so outsiders can't trigger notifications | Application |
| **Secrets in code** | Secrets stay out of the repo, and GitHub's secret scanning flags accidental leaks | GitHub |
| **Minimal data** | Store only what features and KPIs need | All |
| **User control** | Users can disconnect their bank and delete their account and all data | All |
| **Dependency safety** | GitHub Dependabot alerts for vulnerable packages | GitHub |

## GitHub Workflow

| Practice | How It Works |
| --- | --- |
| **Repository** | Week 3 – ADHD Budgeting App (public) |
| **Branches** | `main` is production; each task gets its own feature branch |
| **Pull requests** | All changes merge through pull requests, and `main` is protected from direct pushes |
| **Preview deployments** | Vercel builds a preview link for every pull request, so changes can be tested before merging |
| **Production deployment** | Merging to `main` deploys to production automatically |
| **Database changes** | Supabase migrations (database schema changes) are saved in the repo, so the database setup is version-controlled |
| **Backlog links** | Each pull request references its Notion task |

## Build Phases

*Phases follow dependencies: foundation first, then the epics in the order each one unlocks the next.*

| Phase | Focus | Why This Order |
| --- | --- | --- |
| **Phase 0: Foundation** | Repo, Next.js app, Vercel deployment, Supabase project, authentication, row-level security, progressive web app setup | Every feature depends on accounts and secure data |
| **Phase 1: Epic 1, Effortless Money Tracking** | Plaid and CSV import, Three Buckets, Today's Number, Morning Number notification | Everything else depends on having transactions and Today's Number |
| **Phase 2: Epic 2, Impulse Pause** | Park It, 48-hour prompt, Money Kept | The core differentiator; needs Today's Number |
| **Phase 3: Epic 4, Guilt-Free Comebacks** | Welcome-back summary, money stress check-in, weekly recap | Tests the riskiest assumption; needs activity data |
| **Phase 4: Epic 3, Bill Reminders** | Bill detection and reminders | A Should-have; reuses the notification system |
| **Phase 5: Beta Readiness** | KPI tracking, security review, privacy policy, onboarding polish | Required before inviting real users |
